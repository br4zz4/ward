# Sub-vaults com namespace (myfish::restricted)

> **TLDR**: o nome de vault passa a aceitar `<namespace>::<nome>` (ex.: `myfish::restricted`), cada sub-vault com pasta e chave próprias (`WARD_KEY_MYFISH_RESTRICTED`), endereçado como `myfish::restricted:secrets.*`. `myfish` e `myfish::default` são o mesmo vault. Isso permite separar os segredos abertos ao time dos de produção sem colidir nomes entre projetos.

# what

    Como dono de um projeto com ward, quero criar um sub-vault `myfish::restricted` ao lado
    do `myfish` (default), com chave própria, para dar ao time acesso aos segredos gerais/dev/staging
    sem expor produção, mantendo o nome do projeto no scope e na env da chave.

Glossário: `docs/CONTEXT.md` (Namespace, Sub-vault, Default sub-vault, Canonical vault name).

## Modelo

- **Nome de vault**: `<namespace>` ou `<namespace>::<sub>`. Só um nível de `::`. São inválidos: `a::b::c`, `::b`, `a::`, `:` isolado no nome (`a:b`) e `:::`. Os demais caracteres seguem livres, como hoje.
- **Default sub-vault**: `myfish` ≡ `myfish::default`. O **nome canônico** (usado no tree, no display, na completion e em `--prefixed`) é `myfish`. Qualquer outro sub-vault (`myfish::open`, `myfish::restricted`) é um vault comum, endereçado **só** explicitamente. O `myfish` puro nunca aponta para ele.
- **Scope**: `[vault:]secret-path`, e o `vault` pode conter `::`. O separador vault/path é o primeiro `:` **isolado** (que não faz parte de `::`) antes do primeiro `.`. Exemplos:
  - `myfish::restricted:secrets.production` → vault `myfish::restricted`
  - `myfish:secrets.dev` ≡ `myfish::default:secrets.dev` → vault `myfish`
  - `myfish::restricted` (sem `:` isolado e sem `.`) → o vault inteiro
  - `secrets.dev` / `:secrets.dev` → overlay em todos os vaults, como hoje
- **Layout criado pelo ward**:
  ```
  .ward/config.yaml
  .ward/myfish::default.key          # gitignored
  .ward/myfish::restricted.key       # gitignored
  .ward/vaults/myfish::default/secrets.ward
  .ward/vaults/myfish::restricted/secrets.ward
  ```
  O layout antigo (`.ward/vaults/myfish/` + `.ward/myfish.key` + `name: myfish`) continua funcionando sem migração.
- **Config (flat)**:
  ```yaml
  vaults:
    - name: myfish::default
      path: .ward/vaults/myfish::default
    - name: myfish::restricted
      path: .ward/vaults/myfish::restricted
    - name: commons
      path: $COMMONS_DIR/.ward/vaults/commons
  ```
  O `name` é gravado e regravado como foi declarado (o `ward vault add` não reescreve `myfish::default` como `myfish`).
- **Chave raiz dos arquivos estruturados**: é o nome do vault. No default, a forma gerada pelo ward é `myfish::default:`, e `myfish:` também é aceita (as duas viram a raiz canônica `myfish` no tree). Nos outros sub-vaults é o nome completo, `myfish::restricted:`, que é YAML válido sem aspas. Exemplo:
  ```yaml
  # .ward/vaults/myfish::default/secrets.ward
  myfish::default:
    secrets:
      dev:
        DATABASE_URL: postgres://localhost/myfish_dev
      staging:
        DATABASE_URL: postgres://staging.myfish.internal/app

  # .ward/vaults/myfish::restricted/secrets.ward
  myfish::restricted:
    secrets:
      production:
        DATABASE_URL: postgres://prod.myfish.internal/app
  ```
- **Chaves**:
  | vault | envs aceitas | key files auto-detectados |
  |---|---|---|
  | `myfish` / `myfish::default` | `WARD_KEY_MYFISH`, `WARD_KEY_MYFISH_DEFAULT` | `.ward/myfish.key`, `.ward/myfish::default.key` |
  | `myfish::restricted` | `WARD_KEY_MYFISH_RESTRICTED` | `.ward/myfish::restricted.key` |
  | `myfish::open` | `WARD_KEY_MYFISH_OPEN` | `.ward/myfish::open.key` |

  Na derivação da env, `::` vira `_` (assim como `-` e `.` já viravam). A prioridade continua a de hoje (env auto → `key_env` → `key_file` → global). Se duas fontes do mesmo nível para o mesmo vault estiverem presentes com conteúdos diferentes (as duas envs, ou os dois key files), o comando falha com erro citando as duas. Com conteúdos iguais, segue normal.
- **Validação no load do config** (erro fatal):
  - nome inválido pela gramática acima;
  - `myfish` e `myfish::default` declarados juntos (nome canônico duplicado);
  - dois vaults diferentes cujas envs derivadas se cruzam (ex.: `myfish-restricted` e `myfish::restricted` → `WARD_KEY_MYFISH_RESTRICTED`).
- **Overlay sem qualificador**: sem tratamento especial. O sub-vault entra no overlay como qualquer vault, e quem não tem a chave vê o vault pulado com aviso, como hoje.
- **`--prefixed`**: o `::` do nome canônico vira `_` (`myfish::restricted.secrets.production.DATABASE_URL` → `myfish_restricted_secrets_production_DATABASE_URL`, preservando o case como hoje). Uma colisão com outro path cai na detecção de colisão que já existe.
- **Criação**:
  - `ward init` passa a gerar `name: myfish::default`, a pasta `.ward/vaults/myfish::default/`, a chave `.ward/myfish::default.key` e o stub com raiz `myfish::default:`. O token é impresso como `WARD_KEY_MYFISH_DEFAULT` (e a saída menciona que `WARD_KEY_MYFISH` também vale).
  - `ward vault add <name> [path]`: o path passa a ser opcional (default `.ward/vaults/<name>`). Para qualquer vault novo, o comando gera `.ward/<name>.key`, adiciona ao `.gitignore`, cria a pasta com um `secrets.ward` cifrado (raiz = `<name>`) e imprime o token `WARD_KEY_<NAME>=ward-…`. Quando o path informado já existe com arquivos `.ward`, ele **não** gera chave nem stub: só registra, como hoje.
- **Rotação**: `ward rotate-key [vault]`.
  - Com vault: rotaciona só a chave daquele vault e re-cifra só os arquivos dele. `myfish` e `myfish::default` são o mesmo alvo. A chave precisa estar em key file. Se o vault só tem a chave via env, o comando dá erro (`rotate-key requires a key file for vault <name>`). Se existirem os dois key files do default (iguais), a chave nova é gravada nos dois. O backup vai para `<keyfile>.bkp-<timestamp>` (ex.: `.ward/myfish::restricted.key.bkp-20261115120000`). Ao final, imprime o token novo com o nome da env (`WARD_KEY_MYFISH_RESTRICTED=ward-…`).
  - Sem vault: se o projeto resolve uma única chave (global ou vault único), mantém o comportamento atual, com backup em `<keyfile>.bkp-<timestamp>`. Se houver mais de uma chave distinta entre os vaults, dá erro listando os vaults e pedindo `ward rotate-key <vault>`.

## out of scope

- Migração automática de `.ward/vaults/myfish/` + `.ward/myfish.key` para o layout `myfish::default`.
- Mais de um nível de `::` (`a::b::c`).
- Suporte a Windows: `:` em nome de pasta e de arquivo não é válido lá. Fica como risco aceito, junto com o `rsync`/`scp` interpretando `x::y/` como módulo de daemon (mitigação documentada: usar `./` no path).
- Flag para escolher outro sub-vault como default: o default é sempre `default`.
- Qualquer semântica de acesso ligada ao nome `restricted`. A restrição vem só de quem tem a chave.
- Excluir sub-vaults do overlay sem qualificador.

## acceptance criteria

    Cenário: ler um segredo do sub-vault restricted
      Dado um projeto com vaults "myfish::default" e "myfish::restricted", cada um com sua chave
      E WARD_KEY_MYFISH_RESTRICTED setada
      Quando rodo `ward get myfish::restricted:secrets.production.DATABASE_URL`
      Então recebo o valor de produção

    Cenário: myfish e myfish::default são o mesmo vault
      Dado o vault declarado como "myfish::default" com raiz "myfish::default:" no arquivo
      Quando rodo `ward get myfish:secrets.dev.DATABASE_URL` e `ward get myfish::default:secrets.dev.DATABASE_URL`
      Então os dois retornam o mesmo valor
      E `ward tree` mostra a raiz como "myfish"

    Cenário: raiz "myfish:" também funciona no default
      Dado um arquivo do vault "myfish::default" com raiz "myfish:"
      Quando rodo `ward validate` e `ward get myfish:secrets.dev.DATABASE_URL`
      Então não há violação de estrutura e o valor é retornado

    Cenário: projeto legado continua funcionando
      Dado um projeto com `name: myfish`, pasta ".ward/vaults/myfish" e ".ward/myfish.key"
      Quando rodo `ward secrets` e `ward get myfish:secrets.KEY`
      Então o comportamento é idêntico ao de antes da mudança

    Cenário: qualificador do pai não inclui o restricted
      Dado "myfish" com secrets.staging e "myfish::restricted" com secrets.production
      Quando rodo `ward secrets myfish:secrets`
      Então só aparecem as chaves do default

    Cenário: overlay sem qualificador inclui o restricted
      Dado as duas chaves disponíveis
      Quando rodo `ward secrets secrets`
      Então aparecem as chaves de "myfish" e de "myfish::restricted"

      Dado WARD_KEY_MYFISH_DEFAULT setada (sem WARD_KEY_MYFISH)
      Quando rodo `ward get myfish:secrets.dev.DATABASE_URL`
      Então o vault é decifrado

    Cenário alternativo: envs do default divergentes
      Dado WARD_KEY_MYFISH e WARD_KEY_MYFISH_DEFAULT com valores diferentes
      Quando rodo qualquer comando de leitura
      Então o comando falha citando as duas envs

    Cenário alternativo: key files do default divergentes
      Dado ".ward/myfish.key" e ".ward/myfish::default.key" com conteúdos diferentes
      Quando rodo qualquer comando de leitura
      Então o comando falha citando os dois arquivos

    Cenário alternativo: sub-vault não-default não é alias de myfish
      Dado só o vault "myfish::open" (sem default)
      Quando rodo `ward get myfish:secrets.x`
      Então recebo "vault \"myfish\" not found"
      E WARD_KEY_MYFISH não decifra "myfish::open" (só WARD_KEY_MYFISH_OPEN)

    Cenário alternativo: nomes inválidos
      Dado um config com vault "a::b::c" (ou "::b", "a::", "a:b")
      Quando rodo qualquer comando
      Então o load falha com "invalid vault name"

    Cenário alternativo: default declarado duas vezes
      Dado um config com "myfish" e "myfish::default"
      Quando rodo qualquer comando
      Então o load falha com nome de vault duplicado

    Cenário alternativo: envs derivadas colidem
      Dado um config com "myfish-restricted" e "myfish::restricted"
      Quando rodo qualquer comando
      Então o load falha citando WARD_KEY_MYFISH_RESTRICTED e os dois vaults

    Cenário: criar o sub-vault restricted
      Dado um projeto inicializado
      Quando rodo `ward vault add myfish::restricted`
      Então existem ".ward/myfish::restricted.key" (no .gitignore), ".ward/vaults/myfish::restricted/secrets.ward" cifrado com raiz "myfish::restricted:"
      E o config ganha `name: myfish::restricted` com `path: .ward/vaults/myfish::restricted`
      E o token "WARD_KEY_MYFISH_RESTRICTED=ward-…" é impresso

    Cenário alternativo: vault add em path existente
      Dado um diretório com arquivos .ward já cifrados
      Quando rodo `ward vault add commons ../commons/.ward/vaults/commons`
      Então o vault só é registrado (sem chave nova, sem stub)

    Cenário: ward init no layout novo
      Dado um diretório "myfish" sem .ward
      Quando rodo `ward init`
      Então o config tem `name: myfish::default`, a pasta é ".ward/vaults/myfish::default", a chave ".ward/myfish::default.key" e o stub tem raiz "myfish::default:"
      E `ward secrets` lista secret_1 e secret_2 sem violações de estrutura

    Cenário: rotacionar só o restricted
      Dado os dois sub-vaults com key files
      Quando rodo `ward rotate-key myfish::restricted`
      Então os arquivos do restricted são re-cifrados com a chave nova, os do default ficam intocados (mesmos bytes)
      E existe ".ward/myfish::restricted.key.bkp-<ts>" e o token novo é impresso como WARD_KEY_MYFISH_RESTRICTED

    Cenário alternativo: rotate sem vault num projeto com várias chaves
      Dado vaults com chaves distintas
      Quando rodo `ward rotate-key`
      Então o comando falha listando os vaults e sugerindo `ward rotate-key <vault>`

    Cenário alternativo: rotate de vault com chave só em env
      Dado "myfish::restricted" sem key file e com WARD_KEY_MYFISH_RESTRICTED
      Quando rodo `ward rotate-key myfish::restricted`
      Então o comando falha com "rotate-key requires a key file for vault myfish::restricted"

    Cenário: completion de sub-vault
      Dado os vaults "myfish" e "myfish::restricted"
      Quando completo `ward get myfish::`
      Então é sugerido "myfish::restricted:"
      E completando `ward get myfish::restricted:sec` são sugeridos os paths do restricted

    Cenário: file add em sub-vault
      Quando rodo `ward file add sa.json myfish::restricted:certs`
      Então ".ward/vaults/myfish::restricted/certs/sa.json.ward" é criado cifrado com a chave do restricted

    Cenário: --prefixed com sub-vault
      Quando rodo `ward secrets --prefixed myfish::restricted:secrets`
      Então a env é "myfish_restricted_secrets_production_DATABASE_URL"

    Cenário: plataforma
      Dado macOS (APFS) e Linux (ext4/btrfs)
      Quando rodo a suíte e2e
      Então pastas e key files com "::" são criados, lidos e rotacionados nos dois

# why

Hoje um projeto que quer separar os segredos do time (dev, staging, gerais) dos de produção precisa de dois vaults com nomes soltos. Com `restricted`, a env `WARD_KEY_RESTRICTED` é genérica e colide entre projetos e com vaults externos. Com `myfish-restricted`, o scope vira `myfish-restricted:` e parece outro projeto. Os workarounds (`key_env` explícito) não resolvem: o `WARD_KEY_<NAME>` auto continua sendo checado antes, e o nome do projeto some do scope. Dar ao ward o conceito de sub-vault com namespace resolve as três dores: o nome do projeto aparece no scope e na env, não há colisão entre projetos, e o ward entende que `myfish::restricted` pertence a `myfish` (completion, init, vault add, rotate por vault). O `rotate-key` precisa entrar: com chaves por vault, o rotate global atual re-cifra tudo com uma chave só e quebra o modelo.

# how

TDD em toda task de código: o tester escreve o teste vermelho a partir dos cenários, o builder implementa o mínimo e a suíte fica verde. Validação padrão: `go build ./... && go test ./...` (mais `make test.e2e` quando a task cita e2e). Sem telas (CLI).

Todos os PRs são retrocompatíveis: um projeto sem `::` se comporta como antes em cada etapa. Não há flag; a funcionalidade fica completa no PR 4 e o PR 5 fecha a documentação.

## PR 1 — Gramática de nome e scope (branch: `feat/sub-vaults-1`, base: `main`)
**Entrega:** o ward entende nomes `ns::sub`, nome canônico, envs/key files derivados e scope com `::`. Ainda não é usado pelos comandos de chave.
**Arquivos:**
- Create `internal/config/vaultname.go`:
  - `ValidateVaultName(name) error`: um nível de `::`, sem `:` isolado, sem segmento vazio.
  - `CanonicalVaultName(name) string`: `x::default` → `x`; o resto fica igual.
  - `KeyEnvNames(name) []string`: default → `[WARD_KEY_X, WARD_KEY_X_DEFAULT]`; outros → `[KeyEnvName(name)]`.
  - `KeyFileCandidates(name) []string`: default → `[.ward/x.key, .ward/x::default.key]`; outros → `[.ward/<name>.key]`.
  - `(Source) CanonicalName() string`.
- Modify `internal/config/config.go`:
  - `KeyEnvName` converte `::` em `_` antes de `-`/`.`.
  - `Load` valida os nomes, detecta nome canônico duplicado (`myfish` + `myfish::default`), detecta envs derivadas que se cruzam e auto-detecta key file por `KeyFileCandidates` (os dois presentes com conteúdo diferente → erro citando ambos; iguais → usa o primeiro). `Name` permanece como declarado.
- Modify `internal/secrets/scope.go`:
  - `SplitVaultQualifier(s) (vault, rest string, qualified bool)`: separa no primeiro `:` isolado antes do primeiro `.`. Sem `:` isolado mas com `::` antes do primeiro `.`, a string inteira é o vault.
  - `ParseScope` usa `SplitVaultQualifier` e canonicaliza o vault (`x::default` → `x`).
- Test `internal/config/vaultname_test.go`, `internal/config/config_test.go`, `internal/secrets/scope_test.go`.

**Pronto para prod:** só adiciona funções e validações. Nomes atuais sem `:` passam e scopes atuais parseiam igual (os casos de `scope_test.go` existentes seguem verdes).
**Valida:** `go build ./... && go test ./internal/config/... ./internal/secrets/...`
